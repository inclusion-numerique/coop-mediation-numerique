## 0. Mode d'emploi (agents & skills)

- **Chaque règle a un ID stable** (`DM-3`, `AB-1`…). Cite-les ; ne paraphrase pas.
- **Sévérités** : `BLOCKER` (corriger avant commit) · `WARN` (corriger ou justifier explicitement) · `INFO` (préférence).
- **`convention-reviewer`** : note un diff et sort une ligne par violation :
  `‹ID› ‹SÉVÉRITÉ› ‹cible› — constat — correctif`, où `cible` = `path:line` (violation sur une ligne) **ou** `path/`/`dir/` (violation d'absence ou d'emplacement — fichier manquant, mauvais dossier). Jamais de `:line` inventé. Ne signale **jamais** ce qui est en §9 (choix assumés). Sur un commit/range **historique**, juge l'état tel qu'introduit et le note dans `Périmètre relu`.
- **`domain-modeler`** : §2 est la checklist de conception à satisfaire **avant** d'écrire du code (rend un modèle à valider, pas du code).
- **`feature-auditor`** : parcourt §1–§7 dimension par dimension et produit la liste des résidus.
- **skills `/build-ability`, `/build-feature`, `/build-form`** : §4 = structure à produire ; §8 = process ; §2/§3 = qualité.
- **Structure vérifiée par l'outil** : la place, le nom et la catégorie de chaque dossier et de chaque fichier (ST-1 à ST-7, UI-7, TS-1, l'appariement des tests) sont des règles d'alint, dans `.alint.yml`, lancées par `pnpm lint:structure` et en CI ; une règle de structure qui change se change dans `.alint.yml` et ici, dans le même commit.
- **Imports vérifiés par l'outil** : ce que chaque zone peut importer est une règle de dependency-cruiser, dans `.dependency-cruiser.cjs`, lancée par `pnpm lint:imports` et en CI. Chaque règle part du plus restrictif ; un import admis en plus est une ligne d'une table de données, dans `.dependency-cruiser/<zone>.json`, écrite par cible : la liste exacte des fichiers ou des dossiers qui l'importent ; la config n'accorde à chacun que ses cibles. La config ne porte que les règles, les socles et la génération des règles par dossier ; les tables ne portent que des données. `pnpm lint:imports:tables` reconstruit les tables à partir des seuls imports encore refusés : une ligne devenue inutile disparaît, et un refus qu'aucune table ne couvre arrête le script. Une règle d'import qui change se change dans `.dependency-cruiser.cjs` et ici, dans le même commit. Dans une feature, chaque couche (`domain/`, `action/`, `implementations/<technique>/`, `ui/<rôle>/`, `middlewares/`) n'importe que ses couches voisines admises et le socle de sa couche (`SOCLES` : les outils qui la définissent, comme `zod`, `libraries/model` et `libraries/result` pour le domaine) ; le socle comprend aussi, hors du domaine, les outils génériques (`collections`, `texte`) ; dans les implémentations et l'UI, les libraries de valeurs (`insee`, `telephone`, `nom-affiche`, `departement`, `code-postal`, `adresse`, `texte-riche`) et `libraries/date` ; dans toutes les implémentations, `libraries/result` ; dans l'UI, les libraries d'affichage, d'état d'URL et de formulaire ; les types de pagination et de tri (`@arckit/resultset`) dans le domaine, `prisma`, les présentateurs et les composants ; toute autre library, tout paquet, toute configuration s'ajoute à `couches.json` : la liste exacte des dossiers qui l'importent. Une implémentation n'importe que sa propre technique : le domaine est le pivot, et c'est l'entrée qui compose les techniques ; seul l'adaptateur `next-auth`, qui assemble des fournisseurs, figure en table. Un middleware compose comme une entrée : il peut importer les implémentations de sa feature. Un slot est injecté par `app/` ; une page, un layout, un composant ou un formulaire qui en a besoin le reçoit par une prop, ou bien c'est un composant. Une library n'importe ni `app/`, ni une feature, ni la configuration, ni `jobs/`, ni `cli/` ; elle n'importe qu'elle-même, ses outils de test et les lignes de `libraries.json` (autre library, paquet, module de Node) ; hors d'elle-même, on l'importe par ses entrées. Un module de configuration suit la même règle avec `configuration.json` : il n'importe ni `app/`, ni une feature, ni `jobs/`, ni `cli/`, et s'importe par `index.ts`, `serveur.ts` ou l'index d'un sujet ; `telemetry` et `dsfr` peuvent exporter les composants qui branchent leur service sur le client. Un job importe les domaines et les implémentations des features, et son socle (`configuration/prisma`, `configuration/telemetry`, `libraries/console`, `zod`) ; le CLI n'importe aucune feature, sauf `cli/fixtures` vers les `fixtures/` des features ; le reste est une ligne de `jobs.json` ou de `cli.json`. En plus des règles de zone, `confinement.json` dit, pour chaque paquet sensible (SDK, client Prisma généré, next-auth, axios, exceljs, nodemailer, react-hook-form…), les seuls dossiers qui l'importent, tests, `e2e/` et fichiers racine compris. Le code chargé par Node (domaines, implémentations, tests de composition, CLI, jobs, racine d'une library, entrées d'un module de configuration hors `dsfr`) n'atteint, même indirectement et par un import de type, ni le DSFR ni une feuille de style ; un module `'use client'` n'atteint ni un `serveur.ts`, ni `configuration/prisma`, ni un client généré, ni `server-only`. Un import de type obéit aux mêmes règles qu'un import de valeur.
- **Détection** : chaque règle porte un signal grep-able quand c'est possible (`rg` patterns). Un signal qui matche = candidat violation à confirmer en lecture, pas une certitude.

## 1. Architecture cible (AR) — arborescence & dépendances

Arbre canonique d'une feature :

```
features/<feature>/
├── domain/                      # PUR : 0 import infra, 0 import d'une autre feature
│   ├── <sujet>/                 # sous-dossier par sujet dès 3 fichiers (identifiants/, invitation/…)
│   ├── <value-object>.ts        # defineModel + .brand() + smart constructor
│   ├── <entity>.ts (+ .spec.ts) # entité (champs readonly, discriminated unions)
│   ├── errors.ts · ports.ts     # erreurs métier typées · ports déclarés par la feature
│   └── index.ts                 # seul barrel admis avec implementations/<technique>/index.ts
├── abilities/<ability>/         # 1 cas d'usage = 1 dossier (voir §4)
├── action/ · ui/ · implementations/ # dossiers d'ability remontés à la racine quand leur code sert à plusieurs abilities
├── middlewares/                 # middlewares des server actions et des routes (with-*.ts)
├── implementations/<technique>/ # un dossier par choix technique (prisma/, email/, session/, api/…), jamais de fichier à la racine
├── fixtures/                    # données de démonstration et de test de la feature
└── <sujet>.cucumber.ts          # hooks et steps Cucumber partagés par les abilities, seulement à la racine
```

Une feature sans ability qui porte une règle de domaine a aussi, à sa racine, `<feature>.feature.md` et `<feature>.steps.ts` (TS-1).

Rien d'autre à la racine d'une feature : ni `index.ts`, ni `server.ts`, ni fichier posé à plat.

### Structure et nommage (ST)

| ID   | Règle | Sévérité |
|------|-------|----------|
| ST-1 | Noms de fichiers et de dossiers en **kebab-case**, sauf un `.tsx` dont l'export principal est un composant (**PascalCase**). **Français pour le métier**, **anglais pour la technique** (`prisma/`, `session/`, `.query`, `.transfer`). | BLOCKER |
| ST-2 | **Barrels** : dans une feature, admis seulement dans `domain/index.ts` et `implementations/<technique>/index.ts`, d'une feature ou d'une ability ; ailleurs dans une feature (racine de feature ou d'ability, `ui/`, `fixtures/`, `middlewares/`), on importe le fichier qui définit le symbole. Une **library** et un **module de configuration** s'importent au contraire par leurs **entrées** : l'`index.ts` de la racine, en TypeScript pur chargeable partout (Node compris), dès que la racine porte des fichiers ; l'`index.ts` de chaque sujet de premier niveau (`@/libraries/<library>/<sujet>`), qui peut exiger un bundler (composants) ou le serveur ; pour un module de configuration qui mélange les environnements, `serveur.ts` à côté d'`index.ts`. Un sujet est homogène : s'il doit exister dans deux environnements, il se dédouble en `<sujet>` et `<sujet>-serveur` ou `<sujet>-client`. Une entrée, comme tout barrel, ne contient que des réexports nommés : ni `export *` (Biome `noReExportAll`), ni code, ni directive ; le code vit dans un fichier nommé d'après son contenu, et un module réexporté n'a aucun effet au chargement. Un import dynamique (`import()`) vise le fichier, pour garder le découpage du bundle. | BLOCKER |
| ST-3 | **Sous-dossier par sujet** pour regrouper des fichiers d'un même sujet, **un niveau au plus** sous un dossier de rôle ; **au plus 32 fichiers à plat** par dossier, tests non comptés, partout dans `src` : au-delà, regrouper par sujet, ou scinder la feature quand le dossier énumère ses cas d'usage (`abilities/`, `app/_actions/<feature>/`). | BLOCKER |
| ST-4 | `implementations/` : **un dossier par technique**, quel que soit son nombre de fichiers, et aucun fichier à sa racine. Une feature ne compose jamais ses abilities : seuls les **points d'entrée** (action, route, page, layout, job, commande du CLI, step, test) branchent les implémentations sur les ports, celles de la feature comme celles des autres ; le doublon de branchement entre points d'entrée est accepté. | BLOCKER |
| ST-5 | **Catégorie** (`nom.<catégorie>.ts`) là où elle dit le rôle : `action/` → `.validation`, `.errors`, `.key`, `.transfer` (saisie → domaine) ; `implementations/<technique>/` → la catégorie dit le rôle, quelle que soit la technique : `.query` (lit : base, API, session, fichier), `.mutation` (écrit ou produit un effet, envoi d'e-mail compris), `.transfer` (traduit entre un format extérieur et le domaine), `.client` (client ou configuration d'un service extérieur), `.sql`, `.where`, `.select`, `.order-by` (fragments de requête), `.payload` (forme des données d'un service extérieur), `.params` (entrée extérieure validée), `.response` (réponse de notre API), `.middleware`, `.classeur` (fichier exporté ou importé), `.adapter` (utilitaire technique), `.email.tsx` (gabarit d'e-mail), `.email-fragment.tsx` (partie partagée par plusieurs gabarits) ; un `.d.ts` augmente les types d'un module extérieur et vit à côté du code qui en dépend ; aucun fichier sans catégorie, hors `index.ts` ; `ui/` → `.presenter` (dans `presenters/`), `.labels` (dans `labels/`), `.search-params` (dans `search-params/`), `.columns` (dans `columns/`), `.validation`, `.form-options`, `.form-data` (dans `forms/`), `.slot.tsx` (dans `slots/`) ; tests → `.spec`, `.integration`, `.stories`, `.cy`. Value objects, entités et fixtures n'en ont pas. | WARN |
| ST-6 | Une **clé d'injection** (`.key.ts`) ne porte qu'une server action et ne vit que dans `action/` : celui de l'ability qui fournit l'action, ou celui du consommateur qui en a besoin hors de cette ability (la racine de la feature, ou une autre feature), qui la déclare avec un type d'entrée structurel sans importer l'ability. | BLOCKER |
| ST-7 | Tests de bout en bout : les **parcours** sur plusieurs pages dans `e2e/*.e2e.ts` ; un test qui ne vérifie qu'une page ou une route est un `page.test.ts` ou `route.test.ts` posé à côté d'elle dans `app`. | BLOCKER |

| ID   | Règle                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Sévérité | Détection                                                                                                                  |
|------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------|----------------------------------------------------------------------------------------------------------------------------|
| AR-1 | `domain/` n'importe **aucune** infra (`@prisma/client` runtime, `next/*`, `react`, fetch). Import **de type** Prisma toléré uniquement si justifié (ex. row shape d'un mapper).                                                                                                                                                                                                                                                                                                                                                                                                            | BLOCKER  | `rg "from '@prisma/client'" features/*/domain` (hors `import type`) ; `rg "from 'next/ \| from 'react'" features/*/domain` |
| AR-2 | Une feature n'importe **jamais** le code d'une autre feature : ni son `domain/`, ni son `index.ts`, ni son `server.ts`. Quand elle a besoin d'une autre feature, elle déclare un port dans son domaine (AR-3). Exception : une feature non refactorée, sans frontière définie, reste importable.                                                                                                                                                                                                                                                                                           | BLOCKER  | `rg --pcre2 "features/(?!<self>)[a-z-]+" features/<self>`                                                                  |
| AR-3 | Besoin d'une autre feature = **branded type local** + **port** dans son domaine. L'implémentation est fournie par les points d'entrée (`app/`, jobs, CLI), qui composent les features : **injection**, composant passé en prop, ou paramètre.                                                                                                                                                                                                                                                                                                                                                                  | WARN     | revue manuelle                                                                                                             |
| AR-4 | Le code partagé entre 2 features vit dans `libraries/` (ou `shared/`), pas dans une feature.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | WARN     | —                                                                                                                          |
| AR-5 | Routes `app/**` = hubs minces : (1) auth, (2) input via value object/schema, (3) données via une **ability** (jamais `prismaClient` brut), (4) rend **une** page ou **un** layout de feature, composé de slots s'il assemble plusieurs abilities ou features (UI-1). | BLOCKER  | `rg "prismaClient\." src/app` |
| AR-6 | Calibrer l'effort DDD au sous-domaine : Core (`activite`, `beneficiaire`) = riche ; Supporting = modéré ; Generic/externe = ACL minimal. Ne pas over-engineer une feature simple.                                                                                                                                                                                                                                                                                                                                                                                                          | INFO     | —                                                                                                                          |
| AR-7 | Une feature peut exposer un **fragment SQL** dans son API publique quand un consommateur doit filtrer, trier ou compter dessus dans une requête paginée — recoller en mémoire y fausserait pagination et totaux. Conditions : le fragment ET ses colonnes vivent dans `implementations/prisma/<entity>.sql.ts` (les appelants n'écrivent jamais l'alias ni un nom de colonne en dur) ; les identifiants injectés sont documentés comme non-paramétrables et sous la responsabilité de l'appelant ; **chaque** requête qui l'embarque — requêtes de comptage comprises — est exercée par un test d'intégration. | WARN     | `rg "Prisma.raw" features/*/implementations/prisma` ; alias SQL (`s1.`) écrit en dur chez un consommateur                                      |

## 2. Domain modeling — checklist de conception (DM)

> **À satisfaire AVANT de coder le domaine** (sur `beneficiaire`, le premier domaine modélisé, 7 itérations de relecture auraient été évitées en appliquant ceci dès le départ). `domain-modeler` répond à chaque point et fait valider le modèle.

| ID      | Règle                                                                                                                                                                                                                                                                                                                                                                               | Sévérité | Détection                                                                                  |
|---------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------|--------------------------------------------------------------------------------------------|
| DM-1    | **Tout primitif métier** = `defineModel(...)` + `.brand('Name')`. Y compris les **enums** (`defineModel(z.enum(...).brand('Name'))`). Aucun littéral string nu.                                                                                                                                                                                                                     | BLOCKER  | `rg ": string( \|$\|\))" features/*/domain` ; champs `string`/`number` nus dans une entité |
| DM-1bis | **Seuil de branding** (résout la tension DM-1 ↔ AR-6) : brander les primitifs **métier** (identifiants métier, quantités, codes, libellés porteurs de règles). **Ne pas** brander les **timestamps système** (`creation`/`modification` → `Date`) ni les ids d'infra sans invariant métier. En cas de doute : brander si le type a une **règle de validation** propre.              | INFO     | un `Date` système brandé ; une quantité métier (`number`) nue                              |
| DM-2    | Le **smart constructor** est le SEUL moyen de créer une instance. Jamais de `as` pour fabriquer une valeur.                                                                                                                                                                                                                                                                         | BLOCKER  | `rg " as [A-Z]" features` (hors `as const`)                                                |
| DM-3    | Chaque `\| null` doit être justifié. Si `null` cache un état → **discriminated union**.                                                                                                                                                                                                                                                                                             | BLOCKER  | `rg "\| null" features/*/domain` → vérifier sémantique                                     |
| DM-4    | Un **boolean qui partitionne** des champs → discriminated union (`anonyme: true/false`).                                                                                                                                                                                                                                                                                            | BLOCKER  | revue : booléen + champs conditionnels                                                     |
| DM-5    | **Deux champs encodant un seul état** → discriminated union (ex. `ContactTelephone`).                                                                                                                                                                                                                                                                                               | BLOCKER  | revue                                                                                      |
| DM-6    | `null` = une valeur d'enum → utiliser la **valeur par défaut** de l'enum, pas `null` (ex. `Genre('NonCommunique')`).                                                                                                                                                                                                                                                                | BLOCKER  | enum nullable dans une entité                                                              |
| DM-7    | Champs **toujours utilisés ensemble** → value object composite (ex. `CommuneResidence`).                                                                                                                                                                                                                                                                                            | WARN     | revue                                                                                      |
| DM-8    | Les **fonctions domaine** prennent des types **validés** (value objects), retournent des types validés, sont **pures** (0 effet, 0 import infra). Le parsing vit à la frontière.                                                                                                                                                                                                    | BLOCKER  | fonction domaine acceptant `string`/row Prisma                                             |
| DM-9    | Tous les champs d'entité sont `readonly`.                                                                                                                                                                                                                                                                                                                                           | WARN     | `rg "^\s+[a-zA-Z]+:" ` sans `readonly` dans un type entité                                 |
| DM-10   | **Transfer layer** (`implementations/prisma/`) : smart constructors Prisma→domaine (valide la DB) ; assignation naturelle domaine→Prisma (les branded types sont structurellement assignables) ; pas de `as`, pas de `!`, `?? defaultValue` + laisser le constructeur valider ; mapper `null ↔ NonCommunique`. **Round-trip test** obligatoire (domaine → fromDomain → toDomain = identité), min + max. | BLOCKER  | absence de `<entity>.transfer.spec.ts`                                                     |
| DM-11   | **Horloge** : l'instant entre dans le domaine par l'entrée `maintenant: Date` de l'objet d'entrée de l'orchestrateur (AB-7). Ni port `() => Date`, ni valeur par défaut, ni paramètre positionnel, ni secondes, ni `new Date()` / `Date.now()` dans `domain/` ; un value object qui dépend de l'année courante la reçoit en paramètre. Le point d'entrée passe `new Date()`. Deux instants distincts = deux entrées nommées. | BLOCKER  | `rg "new Date\(\)\|Date\.now\(\)\|: \(\) => Date" features/*/domain features/*/abilities/*/domain` |
| DM-12   | **Le domaine ne lève ni n'attrape d'exception** : ni `throw`, ni `try`/`catch`, ni `.catch(…)`, ni `.then(ok, ko)`, ni classe. Un port dont l'échec est une issue prévue par le domaine rend un `Result` ; son implémentation attrape l'exception et la traduit en échec tagué (AB-12). Une panne imprévue (base indisponible) peut lever : elle n'est jamais attrapée dans le domaine et remonte au point d'entrée, puis à la télémétrie. Complète AB-5. | BLOCKER  | `rg "\bthrow \|\btry \{\|\.catch\(\(\|\bclass " features/*/domain features/*/abilities/*/domain` |

> **Discriminants multiples (DM-4/DM-5).** Une entité réaliste en porte souvent plusieurs (ex. `anonyme` **et** `ContactTelephone` **et** synchro RDVSP). Choisir comme **discriminant racine** la partition la plus structurante (celle qui conditionne le plus de champs / la présence d'identité) ; modéliser les autres en **unions imbriquées** (value objects dédiés). Ne pas aplatir en une seule union géante, ni multiplier les discriminants racine.

## 4. Structure d'une ability (AB)

```
abilities/<ability>/
├── <ability>.ability.md         # Gherkin (BDD), voir §7
├── <ability>.steps.ts           # steps Cucumber
├── action/                      # contrats d'action : fournis par l'ability ou consommés par elle
│   ├── <ability>.validation.ts  # schéma Zod de l'input (form/wire shape)
│   ├── <ability>.errors.ts      # map erreur domaine → message
│   ├── <ability>.key.ts         # clé d'injection (ST-6)
│   └── <saisie>.transfer.ts     # traduction de la saisie validée vers le domaine
├── domain/                      # si logique métier propre à l'ability
│   ├── <ability>.ts (+ .spec.ts)# orchestrateur : le cas d'usage pur (AB-7)
│   ├── ports.ts                 # ports de l'ability et leur type agrégé (AB-8)
│   ├── errors.ts                # erreurs de l'ability et l'union de ses échecs (AB-12)
│   └── index.ts                 # barrel admis (ST-2)
├── implementations/
│   └── <technique>/             # prisma/ (<x>.query.ts, <x>.mutation.ts), excel/, email/, api/… ; rien à la racine (ST-4)
└── ui/                          # par rôle, voir UI-7
```

Pas d'`index.ts` à la racine d'une ability ; pas de `commands/`, `queries/` ni d'autre dossier.

| ID   | Règle                                                                                                                                                                  | Sévérité | Détection                                                     |
|------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------|---------------------------------------------------------------|
| AB-1 | Ability **avec server action** → contrats groupés dans `action/` (`validation` + `errors` [+ `key`]). Ability **query/pure** → **pas** de dossier `action/`.           | BLOCKER  | `validation.ts` à la racine de l'ability au lieu de `action/` |
| AB-2 | Modèle d'input **partagé** entre abilities → vit dans `features/<feature>/domain/` (pas dans une ability). Plus généralement, tout dossier autorisé dans une ability (`action/`, `ui/`, `implementations/`…) peut **remonter à la racine de la feature** sous le même nom quand son code est commun à plusieurs abilities et que la mutualisation est pertinente. Une ability n'importe jamais une autre ability ; quand l'une consomme le résultat d'une autre, c'est l'entrée (`app`, job) qui l'injecte. En production, la racine n'importe jamais une ability : l'assemblage de plusieurs abilities se fait dans l'entrée, et le typage des ports exige chaque pièce. Seul le code de test de la racine (`fixtures/`, `*.cucumber.ts`, tests d'intégration d'un assemblage) peut importer les abilities de sa propre feature. | BLOCKER  | `rg "abilities/<other>/" abilities/<self>`                    |
| AB-3 | La query/mutation Prisma est **owner-scopée** (`where: { …, mediateurId, suppression: null }`).                                                                        | BLOCKER  | mutation/query sans filtre propriétaire                       |
| AB-4 | Le branding (smart constructors) vit dans l'ability **propriétaire** ; le hub passe des ids, pas des entités brandées d'une autre ability.                             | WARN     | hub qui brande pour le compte d'une autre ability             |
| AB-5 | Erreurs retournées en `Result<T, E>` discriminé (pas de `throw` métier). Dans le domaine, aucune exception du tout (DM-12) ; une implémentation qui appelle un service qui lève attrape et rend un échec tagué. | WARN     | `throw new` dans une mutation/query                           |
| AB-6 | Pas de barrel à la racine d'une ability : les consommateurs importent le fichier qui définit le symbole (ST-2). Le code d'orchestration pur d'une ability vit dans `domain/<ability>.ts`, et reçoit ses dépendances par ses ports ; sa forme est fixée par AB-7 à AB-13. | BLOCKER  | `index.ts` à la racine d'une ability ; dossier `commands/` |
| AB-7 | **Forme de l'orchestrateur**, dans `domain/<ability>.ts` (nom du fichier = nom de l'ability) : `nomDeLAbility = ({ portA, portB }: NomDeLAbilityPorts) => async (entree: { … }): Promise<Result<Decision, EchecDeNomDeLAbility>> => …`. Deux étages ; ports déstructurés ; deuxième étage = **un seul objet nommé**, même pour un seul identifiant brandé (ni positionnel, ni primitif nu, ni étage vide) ; type de retour annoté en ligne, **pas d'alias de signature exporté**. | BLOCKER  | `rg "^export type \w+ = \(" abilities/*/domain` ; `rg "= \(ports: " abilities/*/domain` ; `rg "=> async \(\) =>\|=> async \(\w+: \w+, " abilities/*/domain` |
| AB-8 | **Ports** : chaque port est un type nommé dans `domain/ports.ts` de l'ability ; un port partagé par plusieurs abilities va dans `domain/ports.ts` de la feature (AB-2). Le type agrégé `NomDeLAbilityPorts` vit dans le `ports.ts` de l'ability. Ni type de ports en ligne dans la signature, ni `DependancesXxx`, ni `XxxDependances`. | BLOCKER  | `rg "Dependances" features/*/domain features/*/abilities/*/domain` ; `rg "=> \(\{[^}]*\}: \{" abilities/*/domain` ; orchestrateur sans `ports.ts` voisin |
| AB-9 | **Pas de valeur par défaut sur un orchestrateur** : ni paramètre par défaut, ni port optionnel. Une taille de lot devient une constante du domaine, ou une entrée si le point d'entrée la règle. **Pas de fixtures de test dans `domain/`** : les valeurs d'un test unitaire s'écrivent dans le test (TS-8). | BLOCKER  | `rg "\w+\?: \(" abilities/*/domain/ports.ts` ; `rg "\w+ = [^>]" abilities/*/domain` dans une signature ; `rg --files -g "**/domain/**/fixtures.ts" features` |
| AB-10 | **Tout orchestrateur rend un `Result`** de `@/libraries/result`, y compris s'il ne peut pas échouer (`Result<Decision, never>`). Ni union maison, ni valeur nue, ni chaîne littérale comme succès. | BLOCKER  | orchestrateur dont le type de retour n'est pas `Promise<Result<` ; `rg "success\('" abilities/*/domain` |
| AB-11 | **La valeur de succès porte la décision** : ce que l'orchestrateur a transmis aux ports d'écriture (entité écrite, identité anonyme, invitations enregistrées et échecs d'envoi, relance décidée…), sous un type nommé ; jamais `Result<void>` quand l'orchestrateur écrit. Pas d'événement de domaine. La server action convertit vers la forme qu'elle renvoie déjà : contrat de l'action, UI et messages de `action/*.errors.ts` inchangés. | BLOCKER  | `rg "Result<void" abilities/*/domain` |
| AB-12 | **Erreurs** : toutes dans `errors.ts` (de l'ability, ou de la feature si partagée), de forme `{ readonly _tag: '…' }` + constructeur fonction ; jamais de constante objet, de littéral en ligne, de classe ni de chaîne. L'union `EchecDeNomDeLAbility` est déclarée dans `errors.ts`. Une erreur utilisée par plusieurs abilities d'une feature n'est définie qu'une fois, dans le `domain/errors.ts` de la feature. | BLOCKER  | `rg "_tag: '" abilities/*/domain` hors `errors.ts` ; `rg "^export const \w+ = \{" */domain/errors.ts` ; `rg "^export type EchecDe" abilities/*/domain` hors `errors.ts` ; même `_tag` dans deux `errors.ts` d'une feature |
| AB-13 | **Toute décision métier vit dans un orchestrateur de domaine** ; les implémentations ne font que lire ou écrire (pas de règle, de condition métier ni d'enchaînement de ports dans une `.query`/`.mutation`/`.adapter`). Une implémentation ne branche jamais une autre implémentation (ST-4). Le domaine compose ses propres fonctions pures et l'orchestrateur de sa propre ability, jamais celui d'une autre ability (AB-2). Cas limite admis : la configuration `next-auth`, qui joue le rôle de point d'entrée. | BLOCKER  | condition métier ou appel d'une autre implémentation dans `implementations/**` ; import d'un orchestrateur d'une autre ability |

## 7. Tests (TS)

## 9. Choix assumés (DV) — NE PAS signaler comme violations

> Ces choix sont **décidés**. Un agent ne doit **jamais** les signaler comme des écarts.

| ID   | Choix                                                                                              | Pourquoi                                                                                    |
|------|----------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|
| DV-1 | **Zod** + branded types (`defineModel`), pas Effect Schema                                         | Plus léger, familier de l'écosystème React (ADR-005)                                        |
| DV-2 | Une seule implémentation par port, sauf quand l'environnement de production choisit entre plusieurs techniques réelles (choix fait au point d'entrée) ; jamais d'implémentation en mémoire | Pas d'in-memory : Cucumber joue contre la **vraie base** (ADR-008) ; une seconde technique n'existe que si la production s'en sert (ADR-023) |

| DV-4 | Les routes orchestrent directement, sans builder de page                                           | Les quatre étapes d'une page restent lisibles sans abstraction (ADR-007)                    |

## 10. Ce sur quoi il faut insister (index condensé → règles)

> Vue « radar » pour `convention-reviewer` : les retours récurrents, pointant vers la règle.

- Modèle domaine complet **dès le départ** → §2 (DM-1…10). *Le plus gros levier (7 itérations sur `beneficiaire`).*
- Contrats d'ability dans `action/` ; input partagé en `domain/` de feature → AB-1, AB-2.
- Aucune dépendance inter-ability/feature ; duplication découplée > couplage → IS-1, IS-2.
- Vérifier le remplaçant **avant** suppression → PR-3.
- `app` ne garde que Next et la composition ; module.css→DSFR (pas de déplacement tel quel) → UI-1, UI-2.
- Dans une feature, pas de barrel hors `domain/index.ts` et `implementations/<technique>/index.ts` ; pas d'index d'ability ni de feature ; une library ou un module de configuration s'importe par ses entrées (racine pure, sujets, `serveur`) → ST-2, AB-6.
- kebab-case, français pour le métier, anglais pour la technique ; catégorie là où elle dit le rôle → ST-1, ST-5.
- `implementations/` par technique, `ui/` par rôle, clés seulement dans `action/` → ST-4, UI-7, ST-6.
- Fragment SQL partagé : un seul endroit, colonnes comprises, et chaque requête qui l'embarque testée → AR-7.
- Pas de helper faiblement typé en doublon (primitive partagée) → CS-9.
- Nommage : préfixes au **minimum** (instancier ≠ créer ; `beneficiaireListItem` pas `createABeneficiaire`) ; préfixe seulement s'il porte une info (`seed/to/from/with`) → (nommage).
- BDD = intégration sur chaque ability ; unit seulement si logique pure → TS-1, TS-2.
- Une seule forme d'orchestrateur : deux étages, ports nommés dans `ports.ts`, `maintenant` en entrée, ni défaut ni exception, un `Result` dont le succès porte la décision, erreurs dans `errors.ts` → AB-7…AB-13, DM-11, DM-12.
- Domaine couvert à 100 % par des tests unitaires par le haut, sans logique ni double malin → TS-9, TS-10, TS-11.
- Jamais `git add -A` ; gate avant commit ; présenter le plan puis attendre → PR-2, PR-4, PR-5.
